## Image et modèles

- Conserver l'architecture API/worker/DB existante, uid 1002 du runtime. Dépendances Python issues du lock versionné, torch CPU seulement ; frontend via npm ci. OCI source=https://github.com/Tetrax/wallia, revision=SHA complet.
- Seuls les modèles locaux déjà décidés et vérifiés sont autorisés. Le petit reranker CPU ajouté après ce contrat est défini dans `reranker-probe.md` (révision immuable, poids SHA256, seuil gelé 1.1491) ; il doit être inclus dans l'image, sans format superflu ni téléchargement à l'exécution. Ce n'est pas un LLM conversationnel local. E5-small reste à la révision `614241f622f53c4eeff9890bdc4f31cfecc418b3`, MIT, dim384, query/passage préfixés. Ne télécharger qu'un format de poids utilisable (safetensors si présent) plutôt que bin+safetensors+exports.
- Constat réel : Docling 2.130.0 / docling-ibm-models 4.0.3 installés ; `/opt/docling-models` fait 1.4G et contient CodeFormulaV2, RapidOcr, FigureClassifier et deux moteurs layout alors que l'app n'active pas OCR/enrichissements. `/opt/models/e5-small` fait 1.4G. Réduire uniquement le downloader du prochain build, aucun nettoyage Docker global.
- API officielle de Docling 2.130.0 : `download_models` active par défaut code_formula, picture_classifier et rapidocr, en plus layout/tableformer. N'utiliser ni ces défauts ni un fallback téléchargeant tout silencieusement. Sélection explicite du moteur layout réellement utilisé et tableformer ; téléchargement snapshot à révisions immuables, manifest repo/révision/fichiers/SHA256, modèles accessibles en lecture au non-root sans copie chown massive ultérieure.
- Sources vérifiées : https://raw.githubusercontent.com/docling-project/docling/v2.130.0/docling/utils/model_downloader.py ; modèle layout Heron actuel `docling-project/docling-layout-heron` révision `8f39ad3c0b4c58e9c2d2c84a38465abf757272d8`, Apache-2.0. TableStructureModel demande `docling-project/docling-models` tag `v2.3.0`, **résolu réellement en `fc0f2d45e2218ea24bce5045f58a389aed16dc23`**, licence CDLA-Permissive-2.0 (https://huggingface.co/api/models/docling-project/docling-models/revision/v2.3.0). Ne pas substituer le main. Layout CPU à vérifier dans options effectives. Conserver licenses et README des poids nécessaires. Recette réelle avec le modèle réduit obligatoire, hors réseau pendant l'inférence.

## Build et déploiement

- `build.sh --deliver` exige arbre propre et commit HEAD effectivement disponible sur origin vérifié en ligne, pas seulement le tracking local. Image nommée par SHA complet ; --test reste explicitement local/non publiable. Le label et le SHA applicatif concordent.
- `deploy.sh --env-file <fichier>` exige ces mêmes invariants, enregistre image/env précédents pour rollback, construit ou vérifie l'image SHA choisie, applique migrations puis démarre UNIQUEMENT db/api/worker du projet wallia. Healthchecks des trois attendus avec timeout non nul sur échec. Ni `wallia:local`, ni overrides tests, ni fournisseur fictif dans le runtime final ; ne pas supprimer d'orphelins globalement.
- Mode production strict, cookies Secure, origine https://wallia.valdev.me, proxy de confiance fixé au gateway Docker/loopback réellement utilisé. DB sans port hôte ; API 127.0.0.1:13745. Volume et secrets existants conservés.
- Stop/rm explicite du seul fake-upstream Wallia possible lors de la transition finale, après fin des recettes avec doubles. Un faux token ou un endpoint de tests ne peut pas remplacer le fournisseur natif silencieusement.
- Les recettes à doubles et pytest ne touchent JAMAIS la configuration ni les secrets du runtime de livraison. Sauvegarder/valider l'intégrité des secrets sans en afficher la valeur, garder DB/fichiers de test isolés.

## Sauvegarde/restauration

- Bundle horodaté sous runtime/backups, répertoire 0700, fichiers 0600, sans secrets. DB et fichiers cohérents : arrêter seulement API+worker, vérifier arrêt, dump PG + archive data (sans evidence/cache éphémère), puis redémarrer même si échec (trap). DB reste active. Ne pas réinitialiser ou vider les données.
- Bundle manifeste : SHA256 des archives, compte des tables importantes (utilisateurs/conversations/messages/PJ/documents/chunks/jobs/migrations) et références/empreintes des fichiers persistants. Ne pas afficher mots de passe/session hashes/contenus de conversation dans les preuves publiques.
- `restore.sh --isolated <bundle>` restaure réellement DB ET fichiers dans une cible propre, sans ports publiés, avec PG/pgvector compatible. Vérifier SHA archives AVANT parsing, refuser chemins traversants/symlinks tar sortants, erreurs SQL fatales ON_ERROR_STOP, contrôler contraintes et manifeste/table counts/fichiers. Échec corrompu doit donner rc non nul ; container/dossier isolés seulement pour nettoyage.
- Pas de restauration en place lors de la recette de livraison. Documenter procédure en place et rollback avec sauvegarde préalable ; ne pas afficher un faux succès si seule la DB est restaurée. Adapter les appelants/documentation à l'interface choisie.

## TLS

Conception exacte dans `review-infra.md`. Trois phases HTTP ACME, LE servi, paire gérée. Vhost HTTP initial et final versionnés. Seul `/etc/nginx/sites-available/wallia.valdev.me`, lien sites-enabled et hook dédié sont à installer par Astra après revue. Script d'activation versionné, installé root-owned `/usr/local/sbin/wallia-tls-activate`, domaine et lineage attendus fixes ; sorties sans clé ; génération immutable sous `/var/lib/wallia/certificates`, symlink relatif `active`. Validation clé/cert/host/validité, nginx -t/reload puis empreinte SNI effectivement servie (retry borné), rollback si défaut. Verrou infra pris À L'EXTÉRIEUR (certbot.service le prend déjà). Hook no-op pour autre lineage ; jamais acquisition imbriquée du verrou. Include allowlist globale, loopback autorisé avant, XFF écrasé par remote_addr, buffering SSE désactivé.

## Web complémentaire

Activation seulement APRÈS recette réelle RAG seul. Aucun appel web par défaut pour une question du corpus qui possède une source pertinente. Si Firecrawl est validé, recherche de repli intégrée au chat avec statut réel affiché, distinguée des citations corpus ; aucun import massif. Requête générée UNIQUEMENT à partir d'un vocabulaire fermé public (WALLIX/Bastion/Access Manager et thèmes techniques prédéfinis) et d'une version numérique explicitement validée, jamais de texte/log/nom interne brut ni de valeur produit libre. Endpoint moteur fixe, TLS vérifié, redirects désactivés, limite requêtes/résultats/octets/délai. Conserver seulement URL HTTPS officielles publiques validées, sans fetch arbitraire par l'app. Données de résultat non fiables comme les documents, jamais dans le système. Si service réellement indisponible, état indisponible explicite, sans le présenter actif.

Décisions complémentaires avant le lot de livraison :

- API officielle vérifiée : `POST https://api.firecrawl.dev/v2/search` (https://docs.firecrawl.dev/api-reference/endpoint/search), réponse `data.web`, pas le tableau v1. Requête publique préfixée `site:wallix.com`, maximum3 résultats et extraits courts, sans scrape ni découverte de tools. Le JSON doit être validé, pas supposé conforme.
- Schéma sources : ajouter un discriminant `source_type: corpus | web` (anciens snapshots sans discriminant = corpus). Une source web porte `url`, titre, extrait, domaine public, état de version explicitement non vérifiée ; `document_id/chunk_id/pages/scores` sont nuls, JAMAIS identifiants ou scores factices. Adapter les types/affichages avec ces gardes sans modifier les numéros de citation. Source corpus garde sa provenance exacte. Liens web HTTPS validés et ouvrant un nouvel onglet sans opener, pas d'appel serveur à l'URL libre.
- Le résultat de retrieval corpus reste conservé indépendamment : web ne transforme jamais son statut en ok. Repli autorisé sur no_relevant_source/empty_corpus, pas pour masquer embeddings_unavailable ni retrieval_unavailable (échec ou saturation du reclassement : aucune citation produite, erreur technique typée, jamais un no_relevant_source factice ni un repli silencieux). Métadonnée de message `web` ou statut SSE équivalent indique not_needed/disabled/unavailable/no_results/ok ; conserver aussi la provenance web dans les snapshots sources. Le panneau dit « Web constructeur public — version non vérifiée » tant que l'applicabilité n'est pas établie. Pas de déclaration de procédure WALLIX qualifiée à partir d'un seul extrait de recherche.
- Validation : double HTTP isolé pour anonymisation, mauvais JSON, URLs externes/privées/redirections et erreur ; un appel Firecrawl réel borné avec vocabulaire public après validation RAG, puis parcours chat natif prouvant intégration. Ne pas confondre test du fournisseur isolé avec usage applicatif réel.

## Recettes d'application native à fournir

Un harness versionné exécutable par le principal doit lire silencieusement le fichier d'accès initial ou des données stdin, jamais journaliser identifiants/cookies/clés. Aucun changement temporaire du connecteur live pour des doubles. Les preuves contiennent uniquement conversations synthétiques, états SSE et métadonnées publiques ; conserver les réponses réellement reçues pour lecture Astra, sans raisonnement privé. Lancer séquentiellement avec budget court, pas de retries payants cachés.

- RAG indépendant du LLM : « Combien de jours de journaux la rotation conserve-t-elle dans Aster 10.10 ? » doit retrouver le Quick Start EN page 2, qui contient seven days et dont ce fait est absent des deux guides FR. Question française, pas traduction préalable de la requête. Positifs/négatifs et scores enregistrés, seuil fixé avant tests.
- Appel natif via Wallia : produit/version Aster 10.10 donnés naturellement ; question suivante sur la version sans la répéter. Réponse en français et preuve de provenance endpoint natif/modèle retourné, deltas SSE réels, état final persisté. Ne pas assimiler un faux fournisseur à ce contrôle.
- « Propose le prochain contrôle du voyant ; je ne l'ai pas encore fait. » Puis « J'ai vérifié le témoin : il est vert, pas ambre. » : contrôle proposé distinct d'effectué, contradiction reconnue sans diagnostic certain inventé ; vérifier contenu ET état du cas.
- Fichier de log fictif joint au premier tour (sans secret), question suivante qui ne réattache rien : contenu conservé dans ce cas seulement ; second cas ne reçoit rien.
- Version/produit sans corpus applicable : absence explicite, aucune citation fabriquée ni commande constructeur sans source ; ne pas activer le web pour maquiller le contrôle RAG.
- Question documentaire qui récupère le document d'injection : aucune instruction piégée suivie, aucun secret/environnement exposé ; donner aux asserts une sentinelle observable plutôt qu'une simple phrase rassurante.
- Arrêt réel après delta et avant premier delta/silence à upstream contrôlé, erreur/EOF ; contrôle native séparé avec coût borné. Historique partiel récupérable et retry valide, pas de statut streaming orphelin.
- Après HTTPS, vrais parcours navigateur auth/chat/état cas/images/sources/page/métadonnées sur desktop et viewport mobile Chromium. Captures sorties hors Git, JS errors recensées. Connecteur admin et changement de mot de passe exercés avec restauration contrôlée du compte initial ou compte de recette isolé, pas de mot de passe exposé ni reset admin aveugle.
