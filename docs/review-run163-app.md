## Points de lecture jugés améliorés, à confirmer par tests isolés

- Système de prompts statique, contexte non fiable séparé à rôle user ; budget commun, PJ des tours précédents du même cas.
- Sessions/CSRF et downloads contrôlés côté serveur ; clés write-only et erreurs HTTP fournisseur catégorisées.
- Transaction globale courte pour les slots chat ; recovery au démarrage mono-processus et périodique.
- File durable avec garde de claim, lease heartbeat, verrou de session worker, fence publication dans transaction ; Docling subprocess borné et fichiers inchangés.
- Body HTTP limité avant parsing, parseurs upload subprocess terminables ; chemins avec is_relative_to.
- Cohérence demo/scope exigée et liens de citation bornés à la liste serveur.

Le parsing reste dans le cgroup API1200MiB : la borne temps seule ne garantit pas qu'un PDF pathologique ne consommera pas toute la mémoire API avant timeout. Prévoir une limite mémoire/processus ciblée (sans nouveau service) et une preuve de refus contrôlé lors du lot applicatif ; ne pas lancer de PDF-bombe dans le runtime vivant.
